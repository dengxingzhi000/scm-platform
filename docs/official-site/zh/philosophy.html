engineering principles

我们这样构建，
因为边界会说话。

架构不是一组技术偏好，而是一组可被反复执行的判断。下面八条，都是代码里能指到出处的那种： 有选择，也有代价；有做到的，也有明确不做的。

I

隔离先于便利

租户标识不是可选项。缺省即拒绝。

租户在请求入口被解析，而不是在业务代码里被“记得”。TenantFilter 写入线程上下文， TenantInterceptor 在 MyBatis 层给 SELECT、UPDATE、DELETE 追加带别名的谓词， AsyncTenantAutoConfiguration 让异步线程继承同一上下文。默认 scm.tenant.required=true， 缺失即抛出 TenantParseException；单个服务可以关闭 SQL 隔离，但关闭是一个显式动作，不是遗漏。

已知边界也写在这里：JOIN 只对驱动表追加谓词，FROM 里的子查询不会被过滤； 这类复杂查询需要开发者显式补条件。把限制说出来，比让它藏在框架里更安全。

rejected每个服务自己拼 tenant_id —— 一处遗漏就是一整片数据越界。
chosen入口过滤器 + SQL 拦截器统一注入 —— 业务代码不需要“记得”。
cost复杂 JOIN 仍需人工确认；异步任务必须走租户感知执行器。
II

一致性有边界

一个事务，只改一个聚合。

跨库的工作被限制在 service/query/ 与 service/command/；代码库里没有跨数据库 JOIN。 跨服务的强一致交给 Seata AT，每个库都要有 undo_log；订单与库存的预占使用 TCC， 明确实现 confirm 与 cancel 分支；长流程用 scm-common/integration 里的 Saga 编排。

这不是“最终一致性更先进”，而是承认分布式事务的成本，把成本放在能看见的地方： 补偿动作、幂等消费者、可重试的消息。

rejected跨库 JOIN 拼一个大事务 —— 性能不可控，失败后无法定位是谁的回滚。
chosen聚合内强一致 + 跨服务最终一致 —— 每个边界都有对应的补偿。
cost需要 undo_log、TCC 分支、幂等表与对账兜底。
III

契约先于实现

错误响应也是契约的一部分。

统一响应走 ApiResponse；分页保留 MyBatis-Plus 的原始回显（records、total、 size、current），由前端 contracts/page.ts 归一化，而不是在服务端另造一套分页壳。

异常处理按 bean 分治：SecurityRestExceptionHandler 只负责认证、授权与校验， GlobalExceptionHandler 拥有其余异常和 catch-all。这样 404 仍然是 404，405 仍然是 405， 只有应用主动抛出的 ServiceException／BusinessException 消息才允许到达客户端。 过滤器链里的失败走 SecurityErrorResponseWriter，不依赖 advice。

rejected一个 catch-all 接管所有异常 —— 会遮蔽业务异常，并把原始 message 放到公网。
chosen按 bean 明确归属，状态码从异常类型或注解解析。
cost新增异常类型时必须明确它归哪个 handler；契约变更要同步前端。
IV

热与冷，分开走

热路径不等待数据库。

库存扣减、回补与秒杀在 Redis Lua 中原子执行；预占默认 900 秒，支付确认后转实扣，取消或超时释放。 水位告警与每日快照走独立接口，不进入下单链路。订单看板在 PostgreSQL 内聚合，并用 create_time at time zone 与 timestamptz 绑定来避免时区漂移。

Redis 不是账本。它承担承诺与速度，PostgreSQL 承担事实与对账；两者之间的窗口靠补偿、 幂等和对账工作台收敛。

rejected每次扣减都写 PostgreSQL —— 热点行锁与事务开销会把下单延迟放大。
chosen内存原子操作 + 异步落账 + 对账兜底。
costRedis 与账本存在短暂窗口；缓存失效与预占回收必须有任务兜底。
V

先能回滚，再谈上线

演进不是一次性重写，是可持续的替换。

每个服务维护自己的 Flyway 版本线，validate-on-migrate=true、out-of-order=false； 新 schema 变更进 db/migration/V<n>__*.sql，不再往 scripts/db/ 里追加。 读写分离的自动配置默认关闭，需要服务显式设置 spring.datasource.rw.enabled=true； UAA、mTLS、PKCE、两级缓存、数据同步等可选子系统也默认关闭，由服务按需 opt-in。

前端同样渐进：shadcn/ui 与 Tailwind v4 是目标栈，Ant Design 6 只留在存量页面； 不新增 AntD 页面，按域迁移，避免“大爆炸式”重写。

rejected所有服务共享一条迁移线 —— 一个服务的失败会阻塞全部发布。
chosen每服务独立版本线 + 默认关闭的可选能力。
cost跨服务变更需要显式排序；功能默认关闭意味着更多配置与验证。
VI

默认拒绝

默认拒绝比默认方便更难，但更安全。

审计写入只接受内部服务的 HMAC-SHA256 签名，时间窗 5 分钟，控制器没有删除入口； 支付回调在密钥缺失时直接拒绝，而不是“先接受再补验”；权限查询失败时返回 403，而不是放行。 WebAuthn 与 StepUpFilter 负责敏感操作的二次校验。

这些选择会让本地联调更麻烦：必须配密钥、必须带租户头、必须有 scm-system 才能拿到权限。 这是有意的摩擦，不是没做完。

rejected把审计入口开放给任意登录用户 —— 等于允许伪造或抹掉证据。
chosen只接受签名写入；回调未配置即失败；权限查询失败即拒绝。
cost密钥分发与轮换是运维责任；回调配置错误会拒绝合法通知（按设计如此）。
VII

可观测是需求

没有 traceId 的 500，等于没有发生。

5xx 返回通用文案与 X-Request-ID，完整堆栈连同 traceId 写入日志； 每个服务暴露 /actuator/health，指标进入 Prometheus，链路进入 SkyWalking。 错误处理、审计和调用链都围绕同一个请求标识组织，排障时不需要先在日志里“猜时间”。

rejected把 e.getMessage() 直接返回前端 —— 泄漏内部结构，且无法聚合统计。
chosen通用文案 + 请求 ID + 结构化日志。
cost排障依赖日志与追踪系统；埋点与上下文传播需要持续维护。
VIII

非目标

克制不是保守，是不把成本藏起来。

明确不做什么，比明确做什么更难。以下是我们刻意不做的事——它们让剩下的选择更专注。

  • No PaaS不做通用型 PaaS。平台服务的是有供应链领域知识、需要定制与运维掌控的团队。
  • No numbers不写没有压测依据的容量与可用性数字。没有“百万并发”“99.99%”这类装饰性指标。
  • No mesh不引入 Service Mesh。当前规模下，网关 + Nacos + Dubbo 已足够，额外的控制面只会增加故障面。
  • No theater不把未落地的能力写进文档。没有 AI 推理、没有 Canal 同步、没有 ShardingSphere——它们不在运行路径里。
  • No hiding不承诺“零配置”。启动顺序、密钥、租户头与数据库初始化都需要被理解，文档只降低门槛，不替代知识。
原则不是口号，
是下一次改动时的默认答案。
